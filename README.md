# Flutter Tailored Skills

Flutter-focused adaptations of AI agent skills, UI engineering references, and development workflows from across the developer community.

The goal is to help AI coding agents build **thoughtful, polished, accessible, performant, and maintainable Flutter applications** by adapting proven expertise from different ecosystems into Flutter-native guidance.

> This repository is an evolving collection.

## Why this repository?

AI agents can generate Flutter code quickly, but good results require more than syntax and API knowledge. They need practical guidance for design decisions, animation craft, interaction details, performance, accessibility, and reliable implementation workflows.

This repository adapts useful material from existing skill collections and engineering references for Flutter and Dart. It aims to preserve the intent and expertise of each source while translating its examples, tools, and recommendations into idiomatic Flutter practices.

## Adaptation principles

Every adaptation should:

- Preserve the original source's core intent and useful expertise.
- Translate examples and recommendations into **Dart and Flutter**, not merely replace syntax.
- Prefer current stable Flutter/Dart APIs and verify version-sensitive details.
- Respect the target project's SDK constraints, dependencies, architecture, and conventions.
- Avoid forcing a particular state-management solution or package without a clear reason.
- Include platform behavior, accessibility, responsive layout, and lifecycle considerations where relevant.
- Distinguish general principles from source-specific opinions.
- Keep skills focused and use supporting references for detailed material.
- Include practical workflows and verification steps when the task calls for code changes.
- Avoid claiming that code was tested or profiled unless it actually was.

## Keeping skills current

Flutter and Dart evolve continuously. Adaptations should be maintained with these practices:

1. Check official Flutter and Dart documentation and release notes when APIs or behavior may have changed.
2. Prefer stable APIs unless a project explicitly targets prerelease features.
3. Treat the target project's `pubspec.yaml`, lockfile, and SDK constraints as authoritative.
4. Review package APIs against the installed package version.
5. Update examples and references when guidance becomes outdated.
6. Keep version numbers out of general-purpose instructions unless a version is specifically required.
7. Verify skill structure and relative links after editing.
